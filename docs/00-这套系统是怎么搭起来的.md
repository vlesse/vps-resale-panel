# 第 0 章　这套系统是怎么搭起来的

前面 1–10 章教你**用**这套面板。这一章讲的是另一件事：
它是怎么从零建起来的，按什么顺序，每一步做完怎么验收，以及我们在哪些地方栽过。

如果你想从头复刻一套，照着这一章的顺序走。
**特别是「踩过的坑」那几节 —— 那是这份文档里最省时间的部分。**

---

## 0.1 最后长成什么样

一个能真收钱、真开机器的 VPS 转售站。用户在网页上下单付款，一分钟左右
自动拿到一台可以 SSH 进去的机器；机器可能来自谷歌云、AWS，也可能来自
你自己家里那台物理机。

```
                      ┌─────────────────────────────┐
   买家 ──── HTTPS ──►│  面板（Next.js + NestJS）   │
                      │  下单 / 付款 / 控制台        │
                      └──────────────┬──────────────┘
                                     │
              ┌──────────────────────┼──────────────────────┐
              ▼                      ▼                      ▼
      ┌──────────────┐      ┌──────────────┐       ┌──────────────┐
      │  谷歌云 API  │      │ AWS Lightsail│       │  Proxmox API │
      │  下单即开    │      │  下单即开    │       │  你自己的机器 │
      └──────────────┘      └──────────────┘       └──────┬───────┘
                                                          │ 没有公网 IP
                                                          ▼
                                              ┌────────────────────────┐
                                              │ NAT 入口（有公网 IP）  │
                                              │ iptables 端口映射 +    │
                                              │ nginx 二级域名 + 证书  │
                                              └────────────────────────┘
```

**规模**（截至本章写成时）：

| | |
|---|---|
| 后端 | NestJS 11 + Prisma 6 + MySQL 8 + BullMQ，约 10900 行 TypeScript |
| 前端 | Next.js 15 + React 19，17 个页面，约 5700 行 |
| 数据表 | 17 张 |
| HTTP 接口 | 79 条 |
| 机器驱动 | 4 个（gcp / lightsail / proxmox / ssh） |
| 收款驱动 | 5 个（易支付 / USDT-TRC20 / Jeepay / 余额 / 线下转账） |
| 文档 | 11 章，约 11 万字 |
| 自检断言 | 9 节 83 项 |

## 0.2 动手之前要准备什么

| 东西 | 干什么用 | 能不能后补 |
|------|---------|-----------|
| 一台有公网 IP 的 Linux（1 核 1G 起） | 跑面板 | 不能 |
| 一个域名 | 面板的门面，也是支付回调地址的基础 | 不能 |
| Docker + Docker Compose | 整套服务都在容器里 | 不能 |
| 谷歌云账号（开了结算） | 「下单即开」的机器来源 | 能 |
| 一台自己的机器 + Proxmox VE | 卖自建虚拟化 | 能 |
| 支付服务商 / 一个 USDT 钱包地址 | 收钱 | 能（先用线下转账开张） |
| 泛解析 `*.nat.你的域名` | 给 NAT 机器送二级域名 | 能 |

**顺序上唯一的硬约束**：域名要先解析到服务器，HTTPS 才申请得下来；
HTTPS 下来了支付回调才能通。其余都可以边跑边补。

## 0.3 复刻顺序

八个阶段。**每个阶段结束时都有一个能验收的东西**，不要一口气写完再验。

### 阶段一　先把空壳跑起来（半天）

目标：浏览器能打开一个空面板，能注册能登录，数据库里有表。

1. **定数据模型**。先画表再写代码 —— 这套的核心是一张统一的 `machines` 表
   同时覆盖「下单即开」和「库存池」两种履约方式。这个决定影响后面所有模块。
2. **写四个驱动的接口**（`VpsProvider`），实现留空。
   上层只跟接口打交道，加一家新云厂商不用改上层。
3. **Docker Compose 骨架**：mysql / redis / api / web / caddy 五个服务。
4. **鉴权模块**：注册、登录、JWT、验证码。

> 验收：`docker compose up -d` 之后能打开首页、能注册一个账号、
> `docker compose exec mysql mysql -uvps -p vps_resale` 里能看到表。

### 阶段二　接第一家云，打通「下单即开」（一天）

目标：后台加一个谷歌云账号，上架一个套餐，下一单，真的建出一台机器。

1. **建机编排**（`provisioning`）：付款成功 → 入队 → 建机 → 交付。
   **必须是队列**，云厂商建一台机要 30–90 秒，不能让浏览器干等。
2. **谷歌云驱动**：建实例、绑静态 IP、装 BBR、改密码、销毁。
3. **订单 + 支付骨架**：先只做「线下转账」，管理员手工点确认。
4. **失败回滚**：建到一半失败必须把半成品实例销毁 —— 它会一直计费。

> 验收：用真实的谷歌云服务账号密钥，走完「下单 → 标记已付 → 建机 →
> SSH 进去 → 销毁」全流程。销毁后去谷歌云控制台确认实例真的没了。

### 阶段三　让它像个商品（一天）

目标：首页不再是一张表，而是一个能挑的商店。

1. 套餐分区（香港 / 台湾 / 韩国 / 美国 …）
2. **自定义配置档**：用户自己选核心 / 内存 / 硬盘，价格按公式实时算。
   前端算是为了给人看，**服务端必须再算一遍** —— 前端的数字改一下
   就能一块钱买十六核。
3. 后台补齐「修改」和「手工录入机器」
4. 手机上要能买得成东西（表格在窄屏上会把价格和按钮挤出屏幕）

> 验收：拿手机打开首页，从头到尾买一台机器。

### 阶段四　接自建 Proxmox（半天）

目标：卖你自己那台物理机上切出来的虚拟机。

1. 在 PVE 上建一个**专用 API 令牌**，不要用 root 的
2. 准备一个 cloud-init 模板机
3. Proxmox 驱动：克隆、开关机、真重装、销毁

> 验收：下单后 PVE 上真的多出一台虚拟机，能 SSH 进去，退订后真的消失。

### 阶段五　NAT：卖没有公网 IP 的机器（一天）

这是最容易低估的一段。它跨三台机器，任何一环单看都像是「配好了」。

1. **入口机器**：开内核转发，云厂商防火墙放行端口段
2. **隧道**：Tailscale（比手搓 WireGuard 省事得多）
   - PVE 上 `tailscale up --advertise-routes=172.31.0.0/24`
   - **到管理台批准这条子网路由** ← 最容易忘
   - 入口机器 `tailscale set --accept-routes=true`
3. **PVE 上开一个独立私网网桥** `vmbr1`（172.31.0.1/24）+ MASQUERADE
4. **面板侧**：给每台机器分一段公网端口，在入口机器上写 iptables
5. **二级域名**：`m<端口>.nat.你的域名` → 机器的 80，证书自动签

> 验收：从**外网**（不是从入口机器上）`ssh -p 20000 root@入口IP` 能进
> 你家那台虚拟机；`https://m20000.nat.你的域名` 能打开它上面的网页。

### 阶段六　搬到生产域名（两小时）

如果那台机器上已经跑着别的网站（很常见），**不要让面板的 Caddy 去抢 80/443**。

1. 用 `deploy/compose.behind-nginx.yml`：关掉 Caddy、不映射 3306/6379、
   前后端各绑一个只有本机能连的高位端口
2. 已有的 nginx 加一个站点转发过去（`deploy/nginx-panel.conf`）
3. 证书继续交给原来的 certbot 管

> 验收：新面板能打开，**并且那台机器上原有的每一个站点都还是 200**。

### 阶段七　收款（一天）

按「多久能开张」排，不是按「哪个高级」排：

| 顺序 | 方式 | 要申请什么 |
|------|------|-----------|
| 1 | 线下转账 | 什么都不用，今天就能收钱 |
| 2 | 账户余额 | 加一下就有，让老客户不用每次跳支付 |
| 3 | USDT-TRC20 | 只要一个钱包地址，自动到账 |
| 4 | 易支付 | 找服务商开商户，1–3 天 |

> 验收：每种方式都走一遍真实付款。余额那条要额外验
> 「余额不够会不会拒绝」和「重复回调会不会重复加钱」。

### 阶段八　自查（半天）

**这一步不能省。** 我们在这一步查出了七个问题，其中两个会真丢钱，
而它们在前面所有的功能测试里都是「正常」的。

查什么，见 0.5。

## 0.4 踩过的坑

按类别列。每一条都是真栽过的，不是假想。

### 工具和环境

| 坑 | 表现 | 怎么办 |
|----|------|--------|
| **管道会吞掉构建失败** | `docker compose build \| tail -3` 的退出码是 `tail` 的，永远是 0。构建失败了你以为成功了，线上跑的还是旧镜像 | `build > log 2>&1; echo $?` 看真实退出码 |
| **`tsc --noEmit` 查不出 Next.js 的问题** | `page.tsx` 里除了 `default` 之外还导出别的东西，`tsc` 全绿，`next build` 直接失败 | 前端上线前必须真跑一次 `npx next build` |
| **打包时忘了排除 `.env`** | 本地开发的 `.env` 覆盖了服务器上的生产 `.env`，线上跑着 `PANEL_DOMAIN=localhost` 和开发密钥 | `tar --exclude=./.env`，并且部署后核对一下关键变量 |
| **`next build` 不能和 `next dev` 同时跑** | 生产构建覆盖 `.next/`，开发 chunk 全 404。**症状极骗人：页面看着正常但数据全空** | 二选一 |
| Windows 上 tar 把 `D:` 当远程主机 | `Cannot connect to D: resolve failed` | 加 `--force-local` |
| `useEffect(() => load(), [])` | 把 Promise 当成清理函数，StrictMode 下抛错打断 setState | 写成 `useEffect(() => { void load(); }, [])` |

### 谷歌云

| 坑 | 表现 | 怎么办 |
|----|------|--------|
| **`maxResults` 是每页条数，不是总数上限** | 「测试连接」永远转圈且不报错 —— `list()` 默认会一页一页翻完 180 多个机型 | 加 `{ autoPaginate: false }` |
| **角色要 `roles/compute.admin`** | 用 `compute.instanceAdmin.v1` 前面都正常，**到绑静态 IP 那一步才失败** | 它缺 `compute.addresses.create` |
| 组织策略挡住建密钥 | 「Service account key creation is disabled」 | 在组织策略里给这个项目覆盖 `iam.disableServiceAccountKeyCreation` |
| 没有「重装」API | 重装只能销毁重建 | 必须预留静态 IP，否则用户每次重装 IP 都变 |
| SSH 能连 ≠ 初始化跑完 | startup-script 和 sshd 是并行的 | 等 `/var/lib/vps-panel-bootstrap.done` 出现再交付密码 |
| sshd 配置不生效 | 云镜像自带 `60-cloudimg-settings.conf` | 覆盖文件必须 `00-` 开头（先读到的值生效） |

### Proxmox 和 NAT

| 坑 | 表现 | 怎么办 |
|----|------|--------|
| **模板里禁用了 cloud-init 配网** | 虚拟机能开机能登控制台，但网卡是 DOWN 的，面板永远卡在「等待虚拟机拿到 IP」 | 删掉 `/etc/cloud/cloud.cfg.d/99-disable-network-config.cfg` 和写死的 `/etc/netplan/99-*.yaml`，然后 `cloud-init clean` 再转模板 |
| PVE 9 把网桥挪进了 SDN 权限 | 克隆报 `Permission check failed (/sdn/zones/localnetwork/vmbr0, SDN.Use)` | 给令牌加 `PVESDNUser` |
| **BullMQ 按 jobId 去重** | 后台点「重试开通」静默什么都不发生 —— 失败任务保留 7 天，同名任务被丢弃 | 重试时强制新建任务 |
| 回滚留下计费的孤儿 | 建到一半失败，云上机器还在跑，面板毫不知情 | **下达创建指令之前**就把标识落库 |
| Tailscale 子网路由不生效 | 广播了但对端还是不通 | 要去管理台 → Edit route settings 批准 |
| `ip route` 看不到 Tailscale 的路由 | 以为没通 | 它在 table 52，要 `ip route show table all` |
| **nginx 按 SNI 取证书时读不了私钥** | 握手直接断，日志里 `BIO_new_file() failed ... Permission denied` | worker 是 www-data，certbot 私钥是 0600 root。开一个专用组只放这些证书，并装续期钩子 |
| 本地面板和生产面板互相覆盖 | 本地跑一次建机测试，把线上的端口映射清掉了 | 两边都对同一个网关做「声明式整链重写」。测试环境的网关和云账号要停用 |

### 钱

这一类最危险，因为**它们不报错**。

| 坑 | 表现 | 怎么办 |
|----|------|--------|
| **迟到的付款被静默吞掉** | 订单 30 分钟超时取消，用户第 31 分钟才转的账（USDT 链上确认慢，很常见）。代码看状态不对就直接返回成功 —— 钱进来了，东西没给，日志里一行都没有 | 充值照常入账；订单不自动开通但必须吼出来并留备注 |
| **扣款回滚可能白送机器** | 「改订单状态」和「入队建机」不是一个事务。入队失败时订单已经是 paid，再退钱就是钱也退了机器也能开 | 退钱前先确认订单**真的还是待付款** |
| **并发下两张单分到同一个 USDT 金额** | 「查已占用的再挑一个」挡不住并发，一笔转账对上两张单，另一张的用户永远等不到 | 加数据库唯一约束兜底，撞了换金额重试 |
| **管理员邮箱漏进用户流水** | 手工调余额时把操作人邮箱写进了用户能查的流水表 | 记 `operator_id`，不记邮箱 |
| 余额并发扣成负数 | 两个请求同时读到 100，各扣 80，最后 -60 | 用带条件的原子 UPDATE（`where balance >= 金额`），不要先查再扣 |
| 易支付签名怎么调都不对 | 网关只回「签名错误」四个字 | 和 Jeepay 有三处不同：密钥**直接接尾**不是 `&key=`、结果**小写**、`sign_type` 也要排除 |
| 易支付金额差 100 倍 | 传 100 过去人家收一百块 | 它的单位是**元**（两位小数），不是分 |
| 浮点少收一分钱 | `19.99 * 100 = 1998.9999999999998`，截断就是 1998 | 用 `Math.round`，不要 `Math.floor` |
| 值为 `0` 的参数被扔出签名 | `if (v)` 把 `0` 当成假 | 判 `!== undefined && !== null && !== ''` |

## 0.5 自查清单

功能测试全绿不代表没问题。做完之后照这张表再走一遍：

**钱**
- [ ] 余额扣款是不是原子的？（并发能不能扣成负数）
- [ ] 支付回调重发会不会重复加钱 / 重复建机？
- [ ] 付款迟到（单子已超时）会怎样？钱去哪了？有没有人知道？
- [ ] 扣款成功但后续步骤失败，钱退不退？退了会不会变成白送？
- [ ] 金额换算的取整方向对不对？（宁可多收一厘，不能少收一分）
- [ ] 有没有一张**只增不改不删**的流水表？能不能拿它和余额对上？

**权限**
- [ ] 每个用户接口是不是都按 `user.id` 限定了？（能不能查别人的单）
- [ ] 每个管理接口是不是都挂了 AdminGuard？
- [ ] 公开接口有几个？每一个都必要吗？回调靠什么防守？

**隐私**
- [ ] 返回给用户的字段里，有没有内部标识、运营人员的邮箱、别人的信息？

**并发**
- [ ] 有没有「先查再写」的地方？并发下会怎样？
- [ ] 靠代码保证的唯一性，数据库那一层有没有兜底？

**运维**
- [ ] 定时任务重复跑会不会重复处理？
- [ ] 外部服务（支付网关、链上 API、云厂商）挂了会怎样？
- [ ] 测试环境会不会影响生产？（尤其是「声明式重写」这类操作）

我们照这张表查出了七个问题，两个会真丢钱。

## 0.6 关键设计决策

写下来是因为它们会反复被质疑，而每一个都有具体理由。

**统一的 `machines` 表覆盖两种履约方式。**
「下单即开」和「库存池」在业务上差别很大，但在数据上都是「一台机器」。
分两张表的话，控制台、到期、销毁全都要写两遍。

**规则下发是声明式的，不做增量。**
NAT 的 iptables 和 nginx 映射，每次都是**整链重写**。
网关重启过、别人手工动过、上次下发到一半断了 —— 面板都无从知道现场是
什么样子。整链重写则不管现场如何，一次对齐。

**面板只写自己独占的链和文件。**
`PANEL-NAT` / `PANEL-FWD` 两条链，一个被 include 的 map 文件。
Docker、Tailscale、运维手写的规则一根都不碰。
让程序去改别人生产环境的 nginx 主配置，写错一次整台机器上的网站全下线。

**余额只做单币种。**
多币种要么存一套会漂的汇率（账对不平），要么每个币种一个钱包
（用户问「我有 100 块为什么买不了 10 美元的机器」）。
明确拒绝跨币种，是这几种做法里唯一不会悄悄算错钱的。

**面板不存任何私钥。**
USDT 只存收款地址（那本来就是公开信息），提币是运营自己在钱包里做的事。
存了私钥的面板就是个热钱包，一次 SQL 注入等于把钱包端走。

**签证书丢在后台跑。**
签一张要十几秒，还取决于 Let's Encrypt 当时的脸色。
不能让买家的开通流程卡在别人家的服务上 —— 机器先按 HTTP 可用，
证书一分钟内自己补上。

**给用户看的错误必须说人话。**
「网关说签名错误：xxx。商户密钥抄错、前后带空格、或者用了别家的密钥都会这样」
比 `Error: sign invalid` 有用一百倍。这套代码里几乎每个错误分支都是这么写的。

## 0.7 日常维护

**改代码上线，三步缺一不可：**

```bash
# 1. 自检（动了钱相关的代码必跑）
cd apps/api && npx ts-node scripts/selfcheck.ts

# 2. 前端真构建一次（tsc 查不出 Next.js 的问题）
cd apps/web && npx next build

# 3. 打包部署（注意排除 .env，注意看真实退出码）
tar --force-local --exclude=./.env --exclude=./node_modules \
    --exclude=./apps/web/.next --exclude=./.git -czf panel.tgz .
```

服务器上：

```bash
tar xzf panel.tgz -C /opt/vps-panel
cd /opt/vps-panel
docker compose -f docker-compose.yml -f deploy/compose.behind-nginx.yml build api web
echo "构建退出码 $?"          # ← 不要用管道把它吞掉
docker compose -f docker-compose.yml -f deploy/compose.behind-nginx.yml up -d api web
```

**每天看一眼：**

- 后台订单页：有没有「开通失败」和卡在「开通中」超过 10 分钟的
- 后台机器页：有没有孤儿告警（云上真实存在、面板不认识的机器 —— 那在烧钱）
- 后端日志里的 `ERROR`：钱相关的问题都在那里吼

**每月：**

- 对账：后台订单页的已收总额 vs 支付服务商后台的流水

  **对不上就是有 bug**，不是「差一点点没关系」

## 0.8 一个提醒

容器启动命令里是 `prisma db push --accept-data-loss`。
这样能自动跟上 schema 变化，很方便；但如果哪天从 schema 里删掉一个字段，
它会**不吭声地把那一列连数据一起删掉**。

字段只增不减的阶段这样用没问题。要开始改结构了，换成正式的 migration 流程。
